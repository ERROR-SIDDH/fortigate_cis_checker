03 — How it works

One scan, from command to report.

The scanner connects to the firewall, reads configuration, compares each setting with a control, and writes a report. Nothing on the device is changed.

  1. ConnectOver the REST API (HTTPS, recommended) or SSH. With the API, one status call is made first so a wrong host or token fails immediately with a clear message.
  2. ReadEach check asks a shared context for the settings it needs. Every table is fetched once and cached, so ten checks reading system global make one request.
  3. EvaluateEach check returns a result: ID, level, status, what was expected, what was found, and the fix commands. A check that crashes becomes an ERROR result; it never stops the run.
  4. ReportA console summary, plus an optional CSV (one row per check) and a self-contained HTML file with no external resources.

Result statuses

PASSThe setting meets the control.
FAILIt does not. Apply the fix.
WARNPresent but weaker than the control, or a policy choice. Only check 1.7 returns it.
ERRORCould not be evaluated (permission, missing table). An error is not a pass.

Exit codes

0No check failed.
1At least one FAIL (or WARN with --fail-on-warn).
2Could not connect or authenticate.

A non-zero exit lets a scheduled job flag configuration drift.

Compliance score = passing checks ÷ total checks. WARN and ERROR count as not passing. Use --level 1 to score only baseline checks.

Add your own check

  1. Write the ruleAdd rule_name(ctx) to rules.py returning a result. For one system global value, reuse the _global_check helper as checks 1.9 to 1.15 do. Handle both API and SSH.
  2. Register itAppend it to ALL_RULES.
  3. Test offlineAdd the setting to the hardened and weak mock configs in tests/test_rules_mock.py and run the mock test.
  4. Optional fixAdd the setting to FIXES in fixer.py to give it an Apply button. Only single-table settings suit this.

Glossary

FortiGate / FortiOSFortinet's firewall appliance and its operating system. This tool targets 7.x.
CIS BenchmarkA published list of hardening recommendations. These checks are modelled on it but written independently.
Level 1 / Level 2Baseline hardening with little operational cost, versus stricter controls that may affect usability.
API tokenA secret key identifying an API user, sent as a Bearer header.
Access profileA permission set. Each group (system, network, firewall…) is none, read or read-write.
TrusthostThe source IP a user or token may connect from. Requests from elsewhere are refused.
CMDBThe FortiGate configuration database, exposed by the API under /api/v2/cmdb.
VDOMA virtual firewall inside one FortiGate. The default is root.

There is no SSH write path, and deleting undo_state.json loses the ability to undo.

Test a token without running the tool


curl -sk -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $FGT_API_TOKEN" \
  "https://<firewall-ip>/api/v2/monitor/system/status"


200 means the token works; 401 means the token or trusthost is wrong. It prints only the status code, never the token.


Which address does the FortiGate see? The trusthost must be the address the request arrives from, which can differ from your machine's own address behind a VPN or NAT. Lost the token? It cannot be shown again. Run execute api-user generate-key cis_checker_api for a new one; the old one stops working.
